# +50 分层写书管线（串行 → 并行）设计说明

> 版本：1.0.0+50　日期：2026-10-14
> 用户要求：串行写纲要/大纲/细纲/正文，**预设起点与终点、线性补齐中间过程**；
> 主线大纲（串行）→ 分卷大纲（卷间并行、卷内串行）→ 章节细纲（章间并行、章内串行）
> → 正文（章间并行、章内串行）；参考 WeaveGrid 的上下文交互理念；**贴合 RWKV 特性**。

## 一、设计总览

```
作者给定：题材/背景/人物 + 全书起点锚 + 全书终点锚 + 卷数 + 每卷章数
   │
L1 主线大纲        1 个单元（串行）
   │  ① 里程碑规划：把「起点 → 终点」均分成 K 段 → 每卷的卷末状态
   │  ② 大纲正文：把里程碑串成可读主线
   ▼
L2 分卷大纲        K 个单元（卷间并行 / 卷内串行）
   │  每卷：本卷起点（=上卷终点）→ 本卷终点（=L1 里程碑）
   │        → 均分成 M 段 → 每章的章末状态 → 再写成卷大纲
   ▼
L3 章节细纲        K×M 个单元（章间并行 / 章内串行）
   │  每章：上一章状态 → 本章里程碑 → 结构化细纲（8 行 + 伏笔提示）
   │        第二轮：独立核验 + 自动修正（同一会话）
   ▼
L4 正文            K×M 个单元（章间并行 / 章内串行）
      每章：开篇规划轮 → 分片串行续写（RWKV state 增量）→ 清洗 → 质量闸 → 整章重试
```

**「线性补齐」的落地**：每一级都持有一对锚（`PipelineAnchor`：起点状态 / 终点状态），
并把弧线按单元数均分成 `PipelineMilestone` 序列；第 i 个单元结束时必须落在整条弧线的
`i/K` 分位。提示词里明确写死三件事：

1. 第 i 段只完成 `100/K`% 的推进；
2. **不要**在第 1 段就把终点事件写完；
3. **不要**到最后一段还停在起点状态。

这样既不会虎头蛇尾，也不会把结局提前泄掉。

## 二、为什么这个结构天然贴合 RWKV

| RWKV 特性（+50 实测确认） | 管线如何利用 |
|---|---|
| `session_cache: true`：state 存在服务端 | **每个单元一条独立 state 链**（`sessionKey`）→ 单元内严格串行、单元间天然并行 |
| `concurrent_generation: true` | 卷间 / 章间并行有服务端依据（并发数可配，默认 2） |
| O(1) 上下文接续：续跑只发增量 | 同一章第 N 片**不必重发前 N-1 片正文**（Transformer 的 KV Cache 做不到） |
| state 是**单条可变递归状态** | 同一 `sessionKey` 的调用在编排层串行（`_forEachUnit` 按单元分派，不并发同键） |
| 单次生成越长越易 n-gram 循环（+47 实测） | 正文按 ~1400 字切片，用「更多更短的片」凑字数 |
| 上下文窗口 25K | 每单元只吃**自己这一章**的上下文，不被其它章的 turn 稀释 |

## 三、实测踩到的三个 RWKV 服务端坑（都已修）

### 3.1 `/state/*` 无视 `think_type: none`，首轮必输出思考

**现象**：第一次跑案例，5 章里 3 章正文 0 字。原因是 `/state/chat/completions` 的第一轮
总是先吐一大段 `<think>`，把 `max_tokens` 吃光 → 剥离思考后正文为空。

**修法（两层）**：
1. **章内开篇规划轮**（`chapterWarmup`）：每章的第一轮固定成**短**轮
   （`maxTokens: 420`，只要「开场画面 + 第一个冲突点」）——思考自然收束，
   后续分片轮就能拿到干净正文。工艺上也更稳（先定开场再落笔）。
2. **只思考自愈**：若某轮剥离后为空，同一会话再发一轮
   「请直接输出结果，不要再思考」的增量。

**效果**：attempt 1（无修）1/5 过闸 → attempt 2（有修）**4/5**。

### 3.2 结构化任务不能走 state 路由

**现象**：L1 的里程碑规划走 `/state/*`，返回 128 字的畸形片段（JSON 被思考挤掉）。

**修法**：`LayeredChatRequest.stateful` 显式开关 —— 只有 L4 正文链走 state；
L1/L2/L3 走无状态 `/v1/chat/completions`（输出干净、不夹思考）。

### 3.3 模型忽略对象 schema，返回「字符串数组」

**现象**：L1 要求 `[{"index","label","endState"}]`，模型返回 `["状态句1","状态句2",…]`。
原解析器只收 `Map` → 判定解析失败 → 退到行式解析 → 拆出 1 条垃圾里程碑 →
**污染下游全部产物**（主线大纲里出现「第 1 卷（100%）：它由百年前…」这种碎片）。

**修法**：
1. `MilestoneCodec` 接受**字符串数组**，按位置当作 `endState`（不编造 label）；
2. `milestonePlan` 提示词补上**字段含义说明**（label = 名、endState = 状态，别填反）
   与「数组元素必须是**对象**不是字符串」；
3. 校验不合格 → **纠正重试一次**（把问题清单反馈给模型，只重跑这一步，
   不重写已生成的内容 —— 与 WeaveGrid 的「格式错误只重跑解析步骤」同策）。

## 四、其它输出卫生（+50 实测三类污染）

| 污染 | 对策 |
|---|---|
| 开场白（`好的，这是一份…：`） | `cleanStructured`：丢掉**首个契约标记之前**的所有行 |
| Markdown（代码围栏 / `---` / `**`） | 确定性剥离 |
| **模板占位行原样回抄**（`- Txxx（第A章 → 第B章）：…`） | 丢弃含 `Txxx` / `第A章` 的行 |
| 自查轮把细纲改写成对话式散文 | `looksLikeChapterBrief` 契约校验（≥4 个字段名）+ 长度不缩水，**同时**满足才采纳 |

## 五、WeaveGrid 上下文交互理念的落地

| WeaveGrid 的做法 | 本工程落地 |
|---|---|
| 结构先于编纲 | L1 先产出「卷末状态序列」，再据此写 L2/L3/L4 |
| 伏笔三态（设定/提醒/收回）写在细纲里 | L3 要求输出 `## 伏笔提示`；账本从细纲派生 |
| 创作请求读伏笔两端 + 提醒章大纲 | `ForeshadowPrompt.build` 注入 L4（+49 已实现） |
| 对面章节未写时不虚构 | 提示词明确「该章细纲待补，不要虚构其原文」 |
| 独立核验 + 自动修正 | L3 的第二轮自查（同一会话） |
| 格式错误只重跑对应步骤 | L1/L2 里程碑的纠正重试 |
| 前后各两章材料窗口 | L4 注入上一章结尾 + 本章细纲 + 伏笔义务 |

**许可边界**：WeaveGrid 为 PolyForm Noncommercial 1.0.0（版权 amazcutere）。
本实现**只借鉴思路**，未复制其代码 / 提示词 / 数据结构字面量。

## 八、实测结果（同一本书、同 5 章、同端点、同采样参数、同质量闸）

### 8.1 分层方案的**全部运行**（方差是本节最重要的信息）

| 运行 | 正文路由 | 过闸 | 平均字数 | 平均 ngram | 本轮的改动 |
|---|---|---:|---:|---:|---|
| 基线（现有方案） | 无状态 | **5/5** | **2347** | **0.005** | — |
| attempt1 | 有状态 | 1/5 | 596 | 0.000 | 首次实现（思考吃光预算） |
| attempt2 | 有状态 | 4/5 | 1696 | 0.125 | + 开篇规划轮 + 只思考自愈 |
| attempt3 | 有状态 | 1/5 | 560 | 0.182 | + 里程碑兼容 + 纠正重试 |
| attempt4 | 无状态 | 4/5 | 2183 | 0.182 | 改路由为无状态 |
| attempt5 | 无状态 | 4/5 | 2307 | 0.169 | + 输出卫生（回显截断 / 动态伏笔章号 / 末章禁埋） |
| **attempt6** | 无状态 | **5/5** | **2352** | **0.032** | **+ 自查轮改「只回差异补丁」** |
| attempt7 | 无状态 | 4/5 | 2186 | 0.221 | + 伏笔登记规则 + 字段重复确定性警告 |

### 8.2 结论一：**架构成立，正文层与基线相当**

- 过闸 **4–5/5**（基线 5/5）；平均字数 **2183–2352**（基线 2347）——**持平**。
- **attempt6 已经追平基线**：5/5 过闸、2352 字、平均 ngram **0.032**。
- 平均段落重复率 0.000（基线 0.012）——**更好**。

### 8.3 结论二：**方差更大，主导变量是「细纲质量」而不是架构**

同一套分层代码，ngram 在 **0.032 ~ 0.221** 之间摆动（基线稳定在 0.005）。
逐项排查后定位到**唯一主导变量：模型对细纲契约的遵守程度**：

- **字段复制**（`本章目标 == 核心冲突 == 关键转折` 逐字相同）→ 正文反复写同一个节拍。
  attempt5 的第 1、4 章就是这种形态（第 1 章 ngram 0.154）。
- **首轮细纲不合格**（缺契约字段）→ attempt7 的第 2 章出现，直接拖低整体。
- **伏笔小节可选** → attempt5 有 3 条、attempt6/7 是 0 条（模型选择省略）。

⇒ 已针对这三条各自加了确定性对策（见 8.4），**但方差本身来自模型侧**，
客户端只能「检出 + 告警 + 兜底」，不能保证模型一定遵守。

### 8.4 本轮新增的三条对策

| 问题 | 对策（确定性） |
|---|---|
| 字段复制 | `BriefPatch.duplicatedFields` 检出 → ① 写进自查提示词（点名要改哪几项）② **即使模型不改，也把警告注入正文提示词**：「不要把同一个节拍写两遍，把关键转折写成与目标不同的新事件」 |
| 自查轮把核验清单抄进输出（4/5 次被判不合格而丢弃） | **自查轮改为「只回差异补丁」**：模型只输出需要改的 `字段：新值` 行，没有机会复述清单；`BriefPatch.apply` 只替换被点名的字段，其余原样保留。**这一改动把 ngram 从 0.169 压到 0.032** |
| 伏笔小节可选导致不稳定 | 改成**登记规则**：「只要本章出现『留下未解疑问 / 提前暗示 / 只说了一半』的写法，就必须登记一条」——把「要不要埋」换成「把已经暗示的登记下来」 |

### 8.5 分层方案独有能力的实测产出

## 九、总体结论

1. **架构成立且已跑通**：四级管线、锚点线性补齐、层级串行/单元并行、细纲差异补丁自查、
   伏笔账本全部产出可用内容。
2. **正文层与现有方案持平**（字数 2183–2352 vs 2347），段落重复率更好（0.000 vs 0.012），
   最好一轮（attempt6）已在过闸率与复读率上追平基线（5/5、ngram 0.032）。
3. **方差更大**，主导变量是**模型对细纲契约的遵守度**（字段复制 / 缺字段 / 省略伏笔小节），
   不是架构缺陷。已加「检出 + 提示词告警 + 正文兜底」三道确定性对策。
4. **RWKV 有状态路由实测不可用于正文**（`/state/*` 无视 `think_type: none`，
   过闸率 1/5→4/5→1/5 抖动并出现 0 字章）→ 默认关闭并留开关，
   同时把这条作为**给服务端的可复现缺陷报告**。
5. **未出包**：改动全在源码，交付件仍是 +47 的三个包。

## 十、下一步建议

1. **多次重复取均值**：本轮每档只跑 1 次，方差（0.032~0.221）说明单次结果不可作定论；
   建议每档跑 3 次取均值再下结论（这是当前最该补的实验设计）。
2. **接进 App**：`LayeredBookGenerationService` 依赖已全部注入，
   接仓库 + provider 即可在「一键生成」里提供「分层工艺」选项（当前只有命令行入口）。
3. **多卷案例**：本轮是 1 卷 5 章，多卷才能验证「卷间并行」的调度收益。
4. **服务端反馈**：把「`/state/*` 尊重 `think_type`」作为缺陷提给 RWKV 云服务方；
   修好后打开 `proseStateful`，就能真正吃到 O(1) 上下文接续的红利。
5. **细纲契约的强约束**：可考虑让 L3 输出 **JSON**（而不是 8 行文本），
   用结构化解码替代文本契约校验 —— 能同时解决「缺字段」与「字段复制」两类问题。
