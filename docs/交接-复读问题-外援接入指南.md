## 5. 留给外援的难点与开放问题（重点）

### 5.1 复读 vs 停笔的两难 —— 客户端惩罚参数已到极限

两轮真机实验的实测记录（写在 `runtime_settings.dart:218-243` 注释里）：

- 2026-09-30：`alpha_presence 3.0 + dry_penalty_last_n 16000` → 模型**「被罚得不敢写」**，同提示词输出短 30%~51%；
- 2026-10-01：对照官方创作类推荐（`Temperature 1 / Top_P 0.3 / Presence 0 / Frequency 1`），`top_p 0.3` 会让长篇续写**过早停笔**（278 字 vs 1223 字）；混合验证 `top_p 0.5 + presence 0 + frequency 0.6~1.0` → 764/870 字，复读率同为 0.000。

⇒ 结论：**在客户端采样惩罚的参数空间里，「压住复读」和「写得够长」互斥**。+46 之前 `longFormSamplingParams` 选择了中间档（presence∈[0,0.5]、frequency∈[0.6,1.0]、top_p∈[0.45,0.55]），复读在个别章节仍会漏网。外援需要回答：**服务端采样层（albatross 引擎）能否做得更好？** 例如：

- 服务端内置 DRY 采样器（社区公认对长文最有效，llama.cpp 有参考实现；当前 RWKV Cloud **静默忽略 dry_***）；
- 服务端级 n-gram 重复检测 + 自动重采样/回退；
- 确认 `alpha_presence` 大值在服务端的真实语义（是逐 token 罚还是整段罚？是否与 `alpha_decay` 组合正确？）。

### 5.2 服务端是否真正应用 alpha_*（待验证）

客户端已把 alpha_* 发到顶层（④），但**从未在服务端侧验证过这些键真的生效**。验证方法建议：

1. rwkv_lightning / albatross 服务端加参数日志（或查引擎源码的采样入口）；
2. 对照实验：同 prompt，`alpha_presence 0` vs `alpha_presence 2.0`，比较输出 n-gram 重复率（客户端现成的 `RepetitionGuard.charNgramRepeatRatio` 可直接搬去当度量）。

### 5.3 复读触发条件未知

同一套参数下，大多数章节正常、**个别章节退化**。候选诱因（按嫌疑排序）：

1. **上下文回抄**：续写切片把「前文末尾 500 字」拼进 prompt，模型把回抄内容当待续文本再次展开；
2. 上下文接近窗口上限（ctx25600）时 RNN state 质量劣化；
3. 提示词里的大纲字段标签（「本章目标：」等）诱发标签复读（双层前缀的成因之一）；
4. 温度/采样与特定章节内容的共振（随机性，重试即好）。

建议外援用「复读章 vs 正常章」的完整请求体做对比分析。复读样本在用户库 `C:\Users\Administrator\Documents\novelcraft.sqlite` 的 `chapters.notes`（含【AI 修订大纲】块的那几章）。

### 5.4 stop_tokens 语义确认

`[0, 261, 24281]` 是官方默认停止 token（整数 token ID，CUDA 后端约定，`batch_chat.dart:60-64`）。+46 起无状态路由也携带。**需要确认**：这三个 ID 在 g1k 7.2B 词表里的解码内容（261 疑似换行类 token？），确保长文多段落输出不会被过早截断 —— 目前有状态路由一直在发且章节输出正常，风险低，但值得解码验证一次。

### 5.5 兜底持久化语义（已修，需回归盯防）

复读内容能进库的充分条件是：**大纲修订的兜底路径**（模型没按 7 字段格式输出、但清洗后 ≥20 字就当大纲用）**没有复读闸**。+46 已加闸；但类似「非结构化输出仍被宽容采纳」的路径还有别处（如 `RepairedOutline.parse` 的字段级宽容），后续改动要守住一条铁律：

> **凡是「模型输出 → 直接落库」的路径，落库前必须过 `RepetitionGuard.isDegenerate`。**
