## 一、清理「会导致 RWKV 写作异常」的数据与策略

### 1.1 硬编码别的书（最严重）★

`lib/ai/agents/agents.dart` 把**某一本书**（《玄穹剑主》）的书名、题材与 5 个角色
写死在 **system prompt 与回退文本**里。后果：**任何其它项目走这条链路都会被写成
那本书的人物** —— 属典型的「导致模型写作异常的数据」。

| 位置 | 原内容 | 处理 |
|---|---|---|
| Director `GenerateOutline` system prompt | 「你是**《玄穹剑主》**专业主编」 | 去书名，题材由输入决定 |
| Director `CreateWorldSetting` | 「东方奇幻设定总监 / 修炼体系 / 正道魔道妖族」 | 改为「体系形态以用户提供的题材为准」 |
| **Writer `GenerateChapterContent` system prompt** | 「你是**《玄穹剑主》**的网文主笔」+ **叶知秋/谢青山/苏曼莎/冷无霜/血无极 五人语气表** | 去书名与人名，改为「只用用户给定的人物与设定」 |
| Writer `buildUserPrompt` | 缺省塞入「默认角色：叶知秋、谢青山、冷无霜」 | 改为中性提示 |
| WorldSetting agent system prompt | 「东方奇幻设定总监 / 正道魔道妖族三足」 | 中性化 |
| 6 处 `executeTask` 回退文本 | **《玄穹剑主》的正文片段/角色档案/世界观/剧情结构** | 统一改为 `aiUnavailablePlaceholder()`：一眼可辨的失败占位，**不再伪造内容** |

### 1.2 前置设定生成的修仙回退数据

`prerequisite_generation_service.dart` 的回退模板写死了修仙内容（世界地理「九天仙域
四大洲」、灵气体系、法宝等级、练气期寿命、势力「玄天宗/血月宗/万宝商会」、
角色「林轩/苏雨薇/玄天老祖」、末级兜底「练气→…→仙人」）→ 非修仙项目会被塞进
**错误的体系与人物**。已全部改为中性占位（「（待补充：…）」），与文件里原有的
`_createGenericCultivationSystem` 中性策略一致。

### 1.3 诱导「输出思考过程」的提示词

| 位置 | 问题 | 处理 |
|---|---|---|
| `BaseAgent.buildSystemPrompt` 默认值 | 「…**并提供详细的思考过程**」 | 删掉该句，改为「只输出任务要求的最终结果」 |
| `assets/prompts/WriterAgent/GenerateChapterContent.System/{zh,en}.txt` | 「请在创作过程中**展示你的思考过程**」 | 改为正文纪律（只用给定人物、不输出标题/解释、前文已述则不重复） |

对写作类任务，让模型输出思考过程会**挤占正文 token 预算**，且思考文本容易泄漏进正文
（RWKV 批量路由不受 `think_type` 控制，实测会自发吐 `<think>`）。

### 1.4 采样与温度（详见参数报告）

`alpha_decay 0.996→0.999`、`presence` 上限 0.5→2.0、`frequency` 上限 1.0→0.5、
`top_p` 区间 0.45~0.55→0.5~0.7、正文温度 0.88→**1.0**；
RWKV agent 链路正文 `max_tokens` 2048→**4096**（2048 字 < 3200 字定稿闸，此前**数学上不可能达标**）。

## 二、从零成书验证

### 2.1 书籍设定（作者设定，**刻意选非修仙题材**以验证去硬编码）

| 项 | 内容 |
|---|---|
| 书名 | **《低潮图书馆》** |
| 题材 | 都市悬疑 · 轻奇幻 |
| 主题 | 人是否应该改写尚未发生的坏事 —— 以及改写的代价由谁承担 |
| 背景 | 临海小城「潮尾镇」。东岬旧灯塔下有一座**只在退潮时露出水面**的图书馆，馆内每本书记录一件尚未发生的事，按人名编目 |
| 主角 | 沈砚，28 岁，市立图书馆夜班管理员，**轻度面孔失认症**（认不出脸，只能靠声音/习惯认人）→ 只能靠书名上的人名辨认「谁即将出事」 |
| 人物 | 沈砚；周晓棠（海防民警）；老岑（灯塔守）；「编目员」（图书馆主人，从未露脸） |
| 结构 | 3 卷 × 5 章（本次验证第一卷） |

### 2.2 两轮对照（同一本书、同一大纲、同一模型）

工具：`tools/book_craft_smoketest.dart`（**不启动 GUI**，直接跑「章大纲 → 分片续写
（带前文末尾）→ 清洗 → 质量闸」全链路）。

| 轮次 | 工艺 | 过闸率 | 平均 ngram | 平均字数 |
|---|---|---:|---:|---:|
| 第 1 轮 | 片预算 **2.0×**目标（上限 3400）、无整章重试 | **4/5** | 0.256 | 2600 |
| 第 2 轮 | 片预算 **1.5×**目标（上限 2400）、**整章重试 1 次** | **5/5** | **0.053** | 2363 |

第 2 轮逐章：

| 章 | 字数 | ngram | 结果 |
|---|---:|---:|---|
| 1 | 2104 | 0.000 | ✅ |
| 2 | 2220 | 0.000 | ✅ |
| 3 | 2501 | 0.024 | ✅（**首试失败 → 整章重写后通过**） |
| 4 | 2586 | 0.000 | ✅ |
| 5 | 2402 | 0.239 | ✅ |

> 两轮均为**真实模型调用**；第 1 轮失败的第三章**被质量闸拦下、没有落库**，
> 这正是工艺设计的安全语义在工作。

### 2.3 关键因果

第 1 轮失败章的特征：**单次生成冲到 2916 字**（模型超出 1400 字的片目标），
ngram 0.884、段落重复率 0.873，且**退化起点太靠前**（`onset=0`）→
`RepetitionRepair` 判定**不可截断**，只能整章重写。

对照参数实验：2200 token 预算下 0/3 退化；2800 token 预算下出现整章复读。
⇒ **单次生成越长，进入 n-gram 循环的概率越高**。因此工艺改为
「**更短更多片**（1.5× 预算）+ **整章重试**」，用补片循环换稳定性。

## 三、诊断：是项目流程问题，还是模型问题？

**结论：本轮暴露的问题，主因在「项目写作流程/策略」，已可解；模型侧仍有残余问题。**

### 3.1 属项目流程/策略（已修复）

| 问题 | 性质 | 修法 |
|---|---|---|
| 单次生成过长 → 更容易陷入循环 | 流程参数 | 片预算 2.0×→1.5×（上限 3400→2400） |
| 整章偶发复读即判失败、无补救 | 流程缺失 | 增加**整章重试 1 次**（前/后闸各一处） |
| RWKV agent 链路正文 `max_tokens=2048` | 流程参数错误 | → 4096（原值低于 3200 字闸） |
| agent 链路温度硬编码 0.7 | 流程参数 | 任务感知（正文 1.0） |
| system prompt 写死别的书 + 诱导思考过程 | 提示词数据 | 已全部清理（§1.1–1.3） |
| 前置设定回退数据是修仙内容 | 数据 | 中性占位（§1.2） |

### 3.2 属模型/服务端（项目侧无法根治）

| 现象 | 证据 | 说明 |
|---|---|---|
| **单次生成长文仍会概率性复读** | 同一提示词/最优参数下，第 1 轮 1/5 章复读；参数实验中单项臂约 1/3 | 客户端参数空间已到极限；根因在服务端采样层 |
| **长段无段落分隔** | 第 1 轮失败章 `paragraphs=1`（整章一坨） | 模型未按小说惯例输出 `\n\n` |
| **偶发 mojibake 字节** | 失败章出现 `吹得他花ç` | 采样落到非法/异常字节 |
| `dry_*` 被服务端忽略 | 去掉 DRY 后表现无差异 | 社区公认最有效的 DRY 采样器在此不可用 |

## 四、模型后续升级方向建议

1. **state tuning 对齐本项目工艺**（项目已有完整链路：`tools/state_tuning/`）。
   用本轮补强数据集 + v2.3 混采，把「分片续写 + 不越界写长 + 输出段落分隔」的先验注入。
2. **推动服务端补齐 DRY / n-gram 重采样回退**：客户端已无法再压；服务端级
   「检测到 n-gram 循环 → 自动重采样或回退」是最直接的根治手段。
3. **确认 `alpha_decay` 服务端实现**：本轮**正面证实它确实生效且效果显著**
   （0.99→1/3 退化，0.999→0/3），这回答了外援指南 §5.2 的部分疑问；
   建议服务端把 `alpha_decay` 默认值从 0.996 提到 0.999。
4. **段落分隔纪律进训练数据**：把「每 2–5 句一个自然段」写进 SFT 样本，
   当前模型长段一坨的问题会直接拖累成书可读性。
5. **升级到更大 ctx / 更新的 G1K 版本**时，重跑 `rwkv_writing_bench.dart` 的
   `params` + `decay` 两个 suite，确认新模型的 `alpha_decay` 甜点是否仍在 0.999。
