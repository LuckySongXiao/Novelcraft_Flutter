## 一、现状差距：串行写书缺的是什么

改造前，本工程的「跨章一致性」靠的是**提示词拼接**：主线大纲 + 分卷大纲 + 本章大纲 +
上一章结尾。这套机制能维持「文风与情节自然衔接」，但**不保证「埋下的线最终被收」**：

| 缺口 | 后果 |
|---|---|
| 没有伏笔的结构化记录 | 「第 3 章提到的那枚旧铜钱」到第 40 章没人再提，读者当作者忘了 |
| 没有跨章核查 | 回收章写完了，但正文里根本没有兑现——没人发现 |
| 没有密度/节奏视角 | 作者看不到「哪一章埋太多、哪一章收太多」，转折章位置靠感觉 |
| 章号口径不一致 | `Chapters.orderIndex` 是**卷内**序号，作者口中的「第 50 章」是**全书**序号 |

## 二、设计：把「伏笔」变成一份可派生的账本

### 2.1 单一真相：提示就写在细纲里

与参考项目同构 —— **大纲原文即唯一真相，索引是派生物**：

```markdown
## 事件要点
本章陈九潜入祠堂，发现牌位后的夹层。

## 伏笔提示
- T001（第12章 → 第50章；提醒第30章）：一件旧物留下未解疑问。
- T007（第12章 → 第26章）：族谱上被涂掉的一个名字。
```

- 每条**一句、≤50 字、越模糊越好** —— 只留铺垫方向，具体情节留到对应章节再形成；
- 账本**每次都从文本重新解析**，所以不存在「大纲改了但伏笔表没同步」的不一致；
- 提示随细纲一起编辑、审核、回滚、导出（本工程落在「纲要管理」页）。

### 2.2 字段落点（零 schema 变更）

| 内容 | 列 | 上限 |
|---|---|---|
| 章细纲 | `Chapters.summary` | 1000 字（drift 写入校验） |
| **伏笔提示** | `Chapters.notes` | 无上限 |
| 卷大纲 | `Volumes.description` | 1000 字 |

解析时**合并 `summary` + `notes`**（与 `chapter_rewrite_service._outlineOf` 同口径），
所以作者把提示写在哪个字段都能识别。**不新建表、不升 schemaVersion**。

> ⚠ `notes` 现在承载「伏笔提示」这种**编排元信息**，而 `chapter_rewrite_service`
> 会把 `notes` 当「写作依据」喂给正文重写模型 —— 所以那里先调
> `ForeshadowLedgerBuilder.stripSection` 剥掉提示块，避免被当成剧情照抄
>（与历史上 `## 本章大纲（87%）` 被当正文同类的污染）。

### 2.3 章号口径

**全书序号**（按卷序 → 卷内章序展平后的 1..N）。`ForeshadowFlattener.flatten` 负责展平，
`ForeshadowFlattenResult.orderByChapterId` 给出「章 id → 全书序号」；
「纲要管理」页每张章节卡上显示「全书第 N 章」徽标，作者照着写就不会错。

### 2.4 纯规则层的能力（`foreshadow_ledger.dart`）

| 能力 | 说明 |
|---|---|
| **容错解析** | 标题变体（`## / ** / 无标题`）、列表符（`- * • 1.`）、全半角括号、六种箭头、`第20、30章` 并列提醒、`，提醒` 与 `；提醒` 两种分隔 |
| **结构校验** | 跨度 <2、回收早于埋线、编号重复、提醒越界、回收章超全书、提示写错章、说明过长、回收章已写但未兑现 |
| **账本查询** | `setupsAt` / `remindersAt` / `payoffsAt` / `tickAt` / `linkAt` / `overdueAt` / `density` |
| **剧情单元** | 一章回收 ≥5 条即收束当前单元；末章强制收束 → 单元末章 = **转折章** |
| **提示渲染** | `build`（本章联动）/ `buildPayoffAudit`（回收自查）/ `buildDebtReport`（欠债清单） |
| **文本写入** | `formatHint` / `renderSection` / `upsertSection`（原地替换小节，其余内容不动）/ `stripSection` |
| **经纬生成器** | `ForeshadowGenerator.generate` —— 确定性（显式 LCG）、零模型调用、**不生成任何剧情内容**（note 一律留空） |

## 三、接入的写作链路

### 3.1 串行续写（`continue_story_service`）

```
① 汇总 state
①b 构建伏笔账本（展平 → 解析 → 校验）      ← 新增
② 主编决策 JSON：注入「本章要回收/提醒/新埋什么」+「未兑现欠债」  ← 新增
③ 分卷决策
④ 写正文：双 Agent / 回落写手的提示词都注入伏笔块 + 回收自查   ← 新增
⑤ 落库 + 联动同步
```

主编提示词里额外加了硬约束：**「本章要回收」的线必须写进 chapterOutline（写清用什么
具体情节兑现）；有未兑现伏笔时优先安排回收，不要继续拖延。**

### 3.2 整书生成（`multi_agent_book_generation_service`）

新增「**5.3 伏笔经纬结构**」阶段（章大纲规划之后、正文写作之前）：

1. `ForeshadowGenerator.generate(chapterCount: totalChapters, seed: 由书名+章数确定性推导)`
   —— 单元分段、每单元末章 ≥5 条回收、跨度 ≥2、长线跨单元、长跨度给途中提醒；
2. 把提示块写入各**埋线章**的 `Chapters.notes`（成为后续续写/重写/纲要管理的同一份真相）；
3. 正文写作时按章注入「本章义务」（`outlineForWriter(seq)`）——
   ⚠ **只影响提示词**：落库的 `summary` 仍取自原始大纲，提示块不会污染梗概。

种子刻意**不用** `String.hashCode`（不保证跨 Dart 版本稳定），改用显式加权和，
保证「同书名 + 同章数」在任何环境下生成同一套结构。

### 3.3 选节 AI 助手（章节预览）

面板的「AI 参考内容（可手动修改）」新增第 4 栏 **「伏笔联动（本章需回收/提醒）」**，
由预览页装载全书细纲后派生。这样**扩写 / 续写 / 重写 / 润色都不会把已埋的线写断**。

### 3.4 纲要管理（新增「伏笔经纬」页签）

- 顶部工具条：`细纲 / 伏笔经纬` 视图切换 + `生成伏笔经纬` 一键生成；
- 每张章节卡新增「**伏笔提示**」编辑框（落 `notes`）+ 「埋 N · 提醒 N · 回收 N」实时统计；
- 章节卡显示「全书第 N 章」徽标；
- **经纬双轴视图**（`foreshadow_grid_view.dart`，CustomPaint 手绘）：
  上轴 = 设定、下轴 = 收回、弧线连两端、小圆点 = 途中提醒、红色底带 = 转折章、
  两轴旁的密度柱、每 5 章标号、点击某章跳回该章细纲、下方汇总 + 结构问题清单。

### 生成器验收（自检 G 组，最关键的一组）

对 **5 / 12 / 30 / 50 / 120 章**各跑一遍完整闭环：

```
generate(结构) → hintsByChapter(按埋线章分组) → upsertSection(写回各章细纲)
→ ForeshadowLedgerBuilder.build(重建账本)
```

断言：**结构错误 0**、条数一致、跨度与提醒章**逐条保真**。
另有：同 seed 完全一致 / 不同 seed 结构不同 / note 一律留空 / 末章 ≥5 条回收 /
每个单元末章 ≥5 条 / 提醒章严格在两端之间。

## 五、与参考项目的差异（有意为之）

| 维度 | WeaveGrid | 本工程 |
|---|---|---|
| 结构来源 | 内置 Python 生成器（含随机事件/线索名，生成后删除） | 纯 Dart 确定性生成器，**从不生成剧情内容** |
| 存储 | 结构表 + 大纲原文双写 | **只有大纲原文**（`notes`），账本纯派生 |
| 核查 | 独立核查模型角色 + 修订回路 | 规则层产出欠债清单/自查块，注入写作提示词（复用现有链路，不新增模型角色） |
| 编纲方向 | 后向编纲（从结局倒推）+ 正序写作 | 保持既有正向流程；伏笔两端在**埋线时**就确定回收章 |
| 章节编号 | 平铺章节 | 卷 → 章两层，需展平为全书序号 |

## 六、遗留与后续可做

1. **未出包**：改动全在源码里，交付件仍是 +47 的三个包。
2. **多智能体路径的伏笔提示未参与章大纲生成**：当前是「先规划大纲 → 再生成结构 → 注入正文」。
   若要像参考项目那样让大纲本身围绕伏笔写，需要在 `Book/chapterOutline` 提示词里
   加 `{{foreshadowSlots}}` 变量（列出本章允许使用的编号与章号）——这需要先有结构再编纲，
   属于流程顺序调整，建议下一轮做。
3. **回收的语义核查**：目前「回收章已写但未兑现」只能靠规则给出信号 + 提示词自查块。
   真正判断「是否用具体情节兑现」需要一次模型核查（参考项目的 F9 独立核验），
   可复用现有 `book_content_review_service` 的审查链路实现。
4. **倒序编纲**：参考项目「从结局向前编纲」对伏笔回收质量提升明显，本工程尚未支持。
